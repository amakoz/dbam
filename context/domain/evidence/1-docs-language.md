## Lifecycles

### Catalog entry: `draft → active → retired`

Source: `catalog/README.md:11`.

- **Created as `draft`.** The drafter writes it: "Every drafted file is `\"status\": \"draft\"` with null review fields" (`catalog/README.md:89`). Entries can also be hand-written (`catalog/README.md:89`).
- **draft → active.** "Only the owner sets this, after reviewing the entry against its sources, and only together with a review stamp" (`catalog/README.md:14`). The review checklist is in steps 1-6 (`catalog/README.md:118-125`).
- **active → retired.** "Set `\"status\": \"retired\"` instead" of deleting (`catalog/README.md:17`). The documents name no trigger or actor for retiring. The roadmap expects a future AI job whose updates "should land as drafts pending sign-off" (`roadmap.md:216`).
- **Discarding a draft.** An uncommitted, unshipped draft may be discarded: "the never-delete rule does not apply to it" (`catalog/README.md:124`).
- **Missing transitions:**
  - retired → active: not described.
  - active → draft: not described.
  - Unknown whether a POZ sign-off is a state of its own. Today it only replaces the `reviewed_by` value (`catalog/README.md:39`).

### Consent: granted → withdrawn

- **Granted.** Grant = insert with `withdrawn_at` null. "A partial unique index on `(user_id) where withdrawn_at is null` allows one active consent per user" (`archive/2026-09-27-onboarding-profile/plan.md:145`).
- **Withdrawn.** "update own only from active to withdrawn" (`archive/2026-09-27-onboarding-profile/plan.md:148`). Withdrawal "deletes their health data but keeps the consent record as proof" (`archive/2026-09-27-onboarding-profile/plan-brief.md:15`).
- **Re-grant.** "Granting consent again creates a new row." (`archive/2026-09-27-onboarding-profile/plan.md:403`)
- **Re-consent on text change:** open. "decide at the first material change of the consent text whether existing users must re-consent" (`archive/2026-09-27-onboarding-profile/follow-ups/review-fixes.md:11`). Decided for S-03: "New text + version bump, no re-consent" (`archive/2026-09-30-record-appointment-date/plan-brief.md:44`).

### Onboarding: `needs_consent → needs_profile → complete`

- States: `archive/2026-09-27-onboarding-profile/plan.md:246`.
- The dashboard "redirects anything but `complete` to `/onboarding`" (`archive/2026-09-27-onboarding-profile/plan.md:288`).
- Withdrawal "returns them to `/onboarding`" (`archive/2026-09-27-onboarding-profile/plan.md:22`).

## Multiple meanings

1. **"due"** has four senses.
   - (a) **Eligible now, per profile.** This is the dashboard list. "screenings … currently due" (`prd.md:51`). "A user with no due screenings" (`prd.md:56`). The README equates due with recommended: "see which preventive screenings are due for their age and situation" (`README.md:3`).
   - (b) **Due again.** A completion's interval has elapsed. "The exam reappears as \"due\" once its repeat interval elapses" (`prd.md:85`). The due-screening reminder (`README.md:280`).
   - (c) **Due for reminding** in the SQL/claim sense. Appointment rows: "so the same reminders are due again on the next run" (`README.md:265`). The run counter: "`due` counts claimed users" (`README.md:278`).
   - (d) **Research `due_status`.** Never done or overdue = +2, due within 6 months = +1, up to date = 0, and it drives the tier (`screening-catalog-research.md:76,81`). Sense (d) was not adopted: tiers come from evidence level alone (`archive/2026-09-28-screening-recommendations/plan-brief.md:32-33`, "before S-05 there's no due status to sort by").
   - **Ambiguity left open:** "receives an opt-in reminder when a screening becomes due" (`prd.md:32`) "can be read either way" (`archive/2026-10-06-due-screening-reminder/follow-ups/first-time-eligibility.md:5`).
   - **Inference:** "due" is the most overloaded word in the documents and needs one glossary entry per sense.
2. **"screening" vs "exam" vs "check".**
   - The PRD writes "screening/exam" as one idea (`prd.md:40,101`).
   - The documents tend to use "screening" for the catalog type and recommendation ("screening recommendations", `prd.md:45`; "screening catalog", `catalog/README.md:1`).
   - They tend to use "exam" for the user's handled instance ("mark an exam as already handled", `prd.md:32`; "planned exam", "done exam", `README.md:3`; "exam records", `catalog/README.md:15`).
   - "check" appears in the catalog README ("screening checks", `catalog/README.md:3`) and the research ("health check", `screening-catalog-research.md:7`).
   - Polish uses **badanie** for both senses (`archive/2026-10-05-confirm-exam-and-recurrence/plan.md:229`; `archive/2026-10-05-continue-ui-redesign/plan.md:141`).
   - **Inference:** this is a boundary between catalog/recommendation (type) and exam records (per-user instance), blurred by the shared Polish word.
3. **"reminder".**
   - (a) The umbrella for all emails: "Users can opt in to reminder emails: before a recorded appointment, when a done exam is due again, and as a nudge" (`README.md:3`). The heading became "Przypomnienia e-mail" / "Email reminders" (`archive/2026-10-06-follow-up-nudges/plan.md:180`).
   - (b) Specifically the S-04 appointment email ("appointment reminder", `archive/2026-09-30-appointment-reminder/plan-brief.md:8`).
   - (c) PRD FR-012 calls the confirm nudge a "follow-up reminder" (`prd.md:129`).
   - (d) PRD FR-009 calls the due-again email a "recurrence reminder" (`prd.md:120`). It is "scheduled" there (`prd.md:78`), but later documents say nothing is scheduled or stored: it is computed (`archive/2026-10-05-confirm-exam-and-recurrence/plan-brief.md:31`).
4. **"tier" / "importance" / "priority".**
   - US-01 says "ordered by priority" (`prd.md:50`, `prd.md:55`).
   - FR-004's resolution "replaced continuous priority sorting with a simple importance tag/label" (`prd.md:104`).
   - The roadmap speaks of "grouped by importance tier (most important first)" (`roadmap.md:239`).
   - Sorting inside a tier is "`burden_weight` descending, then localized name" (`archive/2026-09-28-screening-recommendations/plan-brief.md:33`).
5. **"plan".**
   - (a) A user's planned exam (`screening_plans`, `archive/2026-09-30-record-appointment-date/plan-brief.md:45`).
   - (b) A 10x implementation plan (`plan.md` files), which is engineering vocabulary.
   - (c) **IPZ, "individual health plan"** (`screening-catalog-research.md:15`).
   - Senses (a) and (c) are both health-domain senses.
6. **"done" vs "confirmed".**
   - "Mark done" (S-03, month precision, any time) and "confirm" (S-05, exact day, only from the appointment date on) both produce a completion (`archive/2026-09-30-record-appointment-date/plan-brief.md:35`; `archive/2026-10-05-confirm-exam-and-recurrence/plan-brief.md:20,28`).
   - The PRD folds both into "confirmed completion" (`prd.md:150`).
   - The UI uses one Polish word, **"Wykonane"**, for the section (`archive/2026-10-27-e2e-core-loop/research.md:75`).
7. **"profile".** It means the health-data profile (`profiles`) and also the `/profile` settings page, which holds both profile edit and reminder opt-in (`archive/2026-09-30-appointment-reminder/plan-brief.md:16`). The opt-in lives on the profile row "so it inherits the consent-gated RLS and dies with the profile on withdrawal" (`archive/2026-09-30-appointment-reminder/plan.md:79`).

## Conflicting statements

Format: older statement → newer statement. The newer one is what the code should be compared with.

1. **Importance labels.**
   - Older: shape-notes, 2026-09-23. FR-004 is "tagged by importance (e.g. important vs. routine)", with "\"important\" like a prostate exam" (`shape-notes.md:126-129`).
   - Newer: PRD v3 (`prd.md:101-105`). Three tiers derived from the evidence level, and "The prostate example is superseded: PSA is a shared decision". The PRD file is dated 2026-09-23 with a "v3, S-02 planning" update, and S-02 was planned 2026-09-28.
2. **AI in recommendations.**
   - Older: the shape-notes decision "AI-driven analysis of user data from the start" (`shape-notes.md:32`), and FR-009 "kept separate from the AI-driven logic that decides which exam to recommend" (`shape-notes.md:146`).
   - Newer: "Revised 2026-09-27: which exams to recommend is also decided by deterministic rules over that curated catalog, not by AI" (`prd.md:123`). Restated in the NFR (`prd.md:137`) and in the roadmap Parked list (`roadmap.md:225`).
3. **Where health data lives.**
   - Older: research. "Compute and store on the device by default" (`screening-catalog-research.md:9`); "Profile in `localStorage`/IndexedDB" and "JSONLogic evaluation in the browser" (`screening-catalog-research.md:168-170`); reminders "stored locally (e.g., .ics export instead of server-side push)" (`screening-catalog-research.md:177`).
   - Newer: server-side, consent-gated storage. The PRD NFR says data "is stored only after the user gives explicit, separate consent" (`prd.md:136`). S-01 (2026-09-27) added the `health_data_consents` and `profiles` tables (`archive/2026-09-27-onboarding-profile/plan-brief.md:22`). S-02 keeps "the profile … server-side" and puts "client-side evaluation" out of scope (`archive/2026-09-28-screening-recommendations/plan-brief.md:37,60`).
