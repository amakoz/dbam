   `entry` / `slug` / `catalog_slug` (…153742:9, schema.ts:258, …093108:15). Comments and props: "exam"
   (`ScreeningActions.astro:19` "The exam's name", api/screenings.ts:11 "the dashboard's exam items"). EN copy
   mixes "screening" (EN:19,132), "exam" (EN:128,142,145,321,327,362) and "test" (EN:56,76,121,124,177) — e.g.
   "Plan this screening" (EN:132) and "Nothing planned yet. Choose … on an exam" (EN:128) on the same panel, "About
   the test" (EN:76). PL uses "badanie" throughout (PL:17,76,136,146) but splits the adjective: "badania
   profilaktyczne" (PL:17,175) vs "badania przesiewowe" (PL:181). Evidence.

   `DoneInput`, `DoneView`, intents `done`/`undone`, i18n namespace `dashboard.screenings.done.*`; comments say "done
   records" (…093108:35 "Completions (done records)", api/consent/withdraw.ts:8) and the ledger comment says
   "completion cycle" (…155313:2). PL "Wykonane"/"oznaczone jako wykonane", EN "Done"/"marked as done". Evidence.
3. **Next due month**: `nextDueMonth`/`nextDue` (rules.ts:180,207), `due_month`/`dueMonth` (…155313:20, due.ts:26),
   comment "due again" (rules.ts:169); PL "Następne badanie: {month}" (PL:157, literally "next exam") vs EN "Due
   again: {month}" (EN:153). Evidence.
4. **Plan's undo vs done's undo**: intent `unplan` → "Usuń z planów"/"Remove from plans" (PL:145, EN:141); intent
   `undone` → "Cofnij oznaczenie" (PL:160) / "Undo" (EN:156). Evidence.

## Implicit concepts

1. **Exam-for-a-user** — no type joins a catalog entry with the user's plan, completion and recommendation; the slug
   is the only identity, and `partitionDashboard` enforces "Each exam shows in one place: a plan wins over a done
   record, and a not-yet-due done record wins over the tier" (rules.ts:223-224). Unique `(user_id, catalog_slug)` on
   both tables (…093108:20,46). Evidence.
2. **Age** — never stored; `age = currentYear - profile.birth_year` (recommend.ts:112), validated 18..120
   (profile.ts:13-14,77-80). The current year comes from `now.getFullYear()` on the dashboard (dashboard.astro:53)
   and in `/api/screenings` (api/screenings.ts:130) but from the Warsaw date in the cron (`warsawToday(now).slice(0,
4)`, due.ts:35). Inference: around New Year the dashboard's runtime year and the cron's Warsaw year can differ;
   behaviour not verified.
3. **Cycle (ledger key)** — each reminder ledger has its own "cycle" column: `appointment_date` in
   `appointment_reminders_plan_date_unique (plan_id, appointment_date)` (…125726:60); `anchor_month` in
   `due_screening_reminders_user_slug_anchor_unique` (…155313:24); `cycle_on` in
   `follow_up_nudges_plan_kind_cycle_unique` (…204148:22). Only the nudge table names it "cycle". Evidence.
4. **Due-again state of a completion** — not stored; derived each time from `anchorMonth` + resolved interval
   (rules.ts:180-185, 275-280); stored only as `due_month` in the ledger once a reminder is claimed (…155313:178).
   Evidence.
5. **Warsaw calendar** — `warsawToday`, `warsawMonth` (rules.ts:55,67) in TS; `'Europe/Warsaw'` literal in SQL
   (…173653:46, …155313:69, …204148:79,84,119,139,144); `isDailySendRun` 10:00 Warsaw (schedule.ts:13). No named
   type. Evidence.
6. **Health data** — a classification, not a type: tables commented "GDPR Art. 9 health data" (…190303:75,
   …093108:24,54, …125726:64, …155313:38, …204148:26); slug treated as health data in the flash cookie
   (`screening_flash`, flash.ts:4-8). Copy: "dane o zdrowiu"/"health data" (PL:173,172, EN:169,168). Evidence.
7. **NFZ program / POZ doctor** — no type; appears in slugs (`*-nfz-program`, catalog/entries/), the evidence-level
   description (schema.ts:235), the `per_program` interval kind and copy "programów NFZ" (PL:19), "lekarzem POZ"
   (PL:50,57,125) / "POZ (primary care) doctor" (EN:51,58). Evidence.
8. **"Open" exams** — the dashboard count `openCount` = items still in tier sections (dashboard.astro:75-76), shown as
   "czeka na Twoją decyzję"/"awaiting your decision" (PL:38, EN:39). Evidence.
9. **Account e-mail** — reminders go to `auth.users.email` (…125726:122, …155313:121); no app table for an account.
   Copy "adres e-mail Twojego konta" (PL:209). Evidence.
10. **Uncollected factor** — `collected: false` (factors.ts:29,55-125) produces the "maybe" branch; 13 of 16 factors
    are uncollected (factors.ts:56-125). Evidence.

## Where business logic lives

No domain layer: entity types are generated DB row types re-exported (`ScreeningPlan`, `ScreeningCompletion`
rules.ts:21-22; `Profile` profile.ts:29), and rules are free functions in `src/lib/**`. Evidence.

- **Eligibility, tier, interval** — pure TS functions (`classifyEntries`, `evaluateBranch`, `resolveInterval`,
  recommend.ts:74-138) over JSON rule data in `catalog/entries/*.json`; rule semantics written as a comment block
  (factors.ts:7-17). Catalog shape is checked three times: Zod `CatalogEntrySchema` (schema.ts:206), hand-written
  `isRuleEntry` (rule-entry.ts:70) and SQL check constraints (…153742:33-52).
- **Dashboard placement, due again, anchor** — pure TS (`partitionDashboard`, `nextDueMonth`, `anchorMonth`,
  rules.ts:172-296); the anchor is duplicated in SQL `screening_anchor_month` ("The only SQL copy of `anchorMonth`",
  …155313:60, comment).
- **Plan/done writes** — orchestrated in the route handler `POST /api/screenings`, including the business check
  "Only exams in the user's current tiers can be planned or marked done" (api/screenings.ts:122-133) and the
  write-done-then-delete-plan order (api/screenings.ts:148-163). Form rules in `parsePlanForm`/`parseDoneForm`
  (rules.ts:123,146).
- **Confirm** — database function `confirm_screening_plan` (…173653:38-74); "Today" computed in the DB.
- **Consent gating** — RLS policies on every health-data table (…190303:98-117, …093108:74-160) plus route-handler
  checks (`hasActiveConsent`, api/profile.ts:28; `getOnboardingState`, api/screenings.ts:101-110).
- **Withdrawal** — database function `withdraw_health_data_consent` (…093108:194-213).
- **Profile validation** — duplicated: TS `parseProfileForm` (profile.ts:69-143) "Bounds mirror the `profiles` check
  constraints" (profile.ts:5, comment) and SQL checks (…190303:55-71).
- **Reminders** — who is due: SQL definer functions (…125726:81-135, …155313:87-230, …204148:56-150); for
  due-screening SQL returns a superset and TS "makes the final call" (…155313:84, comment; due.ts:34); ordering and
  budget in `runReminderChain` (chain.ts:30-70).
- **Opt-in stamp, stale day clearing, updated_at** — DB triggers (…125726:22-43, …180420:12-28, …190303:77-90).
